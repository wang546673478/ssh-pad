# PR 审查流程文档

## 审核流程

```
开发提交 → PR 创建 → 都察院审查 → 反馈修改 → 合并主分支
```

## 审查阶段

### 1. PR 创建阶段 (兵部尚书)

**提交前检查：**
- [ ] 代码在本地编译通过
- [ ] 单元测试通过（覆盖率 > 70%）
- [ ] 代码格式符合 Kotlin Conventions
- [ ] 提交信息清晰描述变更内容
- [ ] 关联 Issue（如适用）

**PR 模板必填项：**
- [ ] 变更描述（What & Why）
- [ ] 影响范围评估
- [ ] 测试方案说明
- [ ] 截图/录屏（UI 变更时）

### 2. 都察院审查阶段 (御史)

**审查时限：** 24 小时内完成初审

**审查流程：**

#### 第一轮：自动化检查
1. CI/CD 构建检查
2. 代码格式检查 (ktlint)
3. 静态分析 (detekt)
4. 单元测试覆盖率

#### 第二轮：人工审查
1. **代码规范审查** (使用 code-review-checklist.md)
2. **安全检查** (使用 security-audit-checklist.md)
3. **架构审查** (Clean Architecture + MVVM)
4. **功能正确性验证**

#### 第三轮：审查意见输出
1. 在 PR 中逐行评论
2. 汇总审查报告
3. 标注优先级（阻塞/建议/优化）

### 3. 反馈修改阶段 (兵部)

**修改要求：**
- 阻塞性问题：必须修复
- 建议性问题：原则上采纳
- 优化性问题：可讨论

**修改时限：** 3 个工作日内

**重新提交：**
- 在原 PR 上追加提交
- 回复审查意见说明处理方式
- 标记为 Ready for Review

### 4. 合并阶段

**合并条件：**
- [ ] 所有阻塞性问题已解决
- [ ] 至少 1 名都察院御史批准
- [ ] CI/CD 全部通过
- [ ] 代码覆盖率达标

**合并方式：**
- 优先使用 Squash and Merge
- 保持主分支历史清晰

## 审查标准

| 维度 | 要求 | 检查方式 |
|------|------|----------|
| 代码规范 | 100% 遵循 Kotlin Conventions | ktlint + 人工审查 |
| 安全检查 | 0 高危漏洞 | security-audit-checklist |
| 架构分层 | 清晰明确 (Data/Domain/Presentation) | 人工审查 |
| 单测覆盖 | > 70% | CI/CD 覆盖率报告 |

## 审查意见格式

### 问题分级

**🔴 阻塞 (BLOCKER)**
- 必须修复才能合并
- 安全漏洞、严重 bug、架构违规

**🟡 建议 (SUGGESTION)**
- 应该修复，但可讨论
- 代码质量问题、可维护性问题

**🟢 优化 (NIT)**
- 锦上添花的改进
- 命名优化、注释补充

### 评论模板

```markdown
### [文件名/行号] 问题简述

**问题类型：** 🔴 阻塞 / 🟡 建议 / 🟢 优化

**问题描述：**
清晰描述问题所在

**修复建议：**
```kotlin
// 建议代码
```

**参考依据：**
- Kotlin Conventions: XXX
- 项目规范：XXX
```

## 审查工具

- **ktlint**: 代码格式检查
- **detekt**: 静态代码分析
- **Jacoco**: 测试覆盖率
- **GitHub PR Review**: 审查意见平台
